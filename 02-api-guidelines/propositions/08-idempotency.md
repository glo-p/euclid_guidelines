# Prop. II.8 - Non-idempotent operations accept an Idempotency-Key

| | |
|---|---|
| **Level** | MUST |
| **Status** | Accepted |
| **Since** | 2026-09-20 |
| **Owner** | Principal engineers |

## Statement

Every `POST` operation that creates a resource or performs an action with side effects MUST accept an `Idempotency-Key` request header (Def. II.10) whose value is a ULID or UUID generated by the client. On receiving a key it has already processed for the same principal and operation within 24 hours, the producer MUST return the original response (same status, headers and body) without repeating the side effect. A reused key with a different request body MUST yield `422` with type `…/idempotency-key-reused`. Operations that are idempotent by nature (`PUT`, `DELETE`) MUST NOT require the header.

## Given

Def. I.16, Def. II.10, Post. I.4, Post. II.5, CN 6, Prop. II.3.

## Demonstration

Under Post. I.4 a client may send a request, lose the connection, and not know whether the side effect happened. Its only safe options are to never retry (losing work) or to retry an operation that is idempotent (Def. I.16). `POST` is not idempotent (Prop. II.3), so the producer must make it so, and the only party that can name "the same intent" across two deliveries is the client, hence a client-generated key. The producer pays for stability (CN 6) by storing the outcome. Replaying the stored response rather than re-executing keeps the effect single while letting the response reach the client. Detecting a body mismatch protects against accidental key reuse, which is a client bug worth surfacing. ∎ Q.E.D.

## Corollaries

* **Cor. II.8.1** - The key is scoped to (principal, operation); two clients cannot collide and a key may be reused on another operation.
* **Cor. II.8.2** - A concurrent duplicate (second request arrives while the first is in flight) yields `409` with type `…/request-in-progress` and `Retry-After`.
* **Cor. II.8.3** - Front-ends generate the key at form submission time, not per retry (Prop. XI.12).

## Construction

Middleware in the project template:

1. Read header; missing on a required operation → `400` `…/idempotency-key-required`.
2. `SET NX` `idem:{principal}:{operation}:{key}` in ElastiCache (Redis) with a 24-hour TTL and status `in-progress`; on failure to set, read the stored record and replay or return `409`.
3. Execute; store `{ requestHash, status, headers, body }`.
4. On replay compare `requestHash` (SHA-256 of canonical body) → `422` on mismatch.

For services without Redis, an `IdempotencyKeys` table in the service database with the same columns and a nightly purge is acceptable (SHOULD prefer Redis for latency).

## Conformance

Spectral `post-has-idempotency-key` (every `POST` declares the header parameter, required unless marked `x-idempotent: true`). Template integration test replays a `POST` and asserts one side effect.

## Scholium

The 24-hour window is a floor. Payment-like operations may keep keys for longer; the contract states the window in the operation description.
