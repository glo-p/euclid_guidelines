# Prop. X.2 - Exceptions expire and are registered

| | |
|---|---|
| **Level** | MUST |
| **Status** | Draft |
| **Since** | 2026-09-20 |
| **Owner** | Principal engineers |
| **Supersedes** | - |

## Statement

An exception ([Def. X.4](../definitions.md#Def.%20X.4%20-%20Exception)) MUST be granted only by an ADR ([Def. X.3](../definitions.md#Def.%20X.3%20-%20ADR)) accepted under [Prop. X.1](01-change-by-pull-request-with-adr.md) that names the service, the proposition, the reason, the compensating control and an expiry date at most 12 months after acceptance. Every exception MUST be listed in the exception register in `adr/README.md` and referenced from the service's conformance manifest ([Def. X.5](../definitions.md#Def.%20X.5%20-%20Conformance%20Manifest)). At expiry the exception MUST be re-reviewed by the principal engineer group and either renewed by a new ADR or closed; an expired exception that is not renewed is a non-conformance.

## Demonstration

[Def. I.20](../../01-foundations/definitions.md#Def.%20I.20%20-%20Exception) makes an exception a recorded, time-bound, approved deviation and says an unrecorded deviation is a defect; [Def. X.4](../definitions.md#Def.%20X.4%20-%20Exception) fixes the record as an ADR and the bound as 12 months. By [Prop. I.2](../../01-foundations/method.md#Prop.%20I.2%20-%20Levels%20and%20their%20obligations) a MUST binds every service unless such an exception exists, so the exception must be as authoritative as the guideline it suspends, which by [Prop. X.1](01-change-by-pull-request-with-adr.md) means an accepted ADR. A deviation with no end date is a permanent fork of the guidelines for one service, which contradicts [CN 8](../../01-foundations/common-notions.md#CN%208%20-%20The%20Whole%20Is%20Not%20Greater%20Than%20Its%20Contracts)'s single architecture; so it expires. By [Post. I.6](../../01-foundations/postulates.md#Post.%20I.6%20-%20Machine%20Verification) an expiry nobody checks is not an expiry; so the register and the manifest make it checkable by machine. ∎ Q.E.D.

## Corollaries

* **Cor. X.2.1** - An exception cannot be granted against a definition, postulate or common notion; those are changed by [Prop. X.1](01-change-by-pull-request-with-adr.md) or not at all.
* **Cor. X.2.2** - A service that is `non-conformant` to a MUST and has no exception is in defect, and the conformance index ([Prop. X.3](03-conformance-manifest.md)) shows it as such.

## Construction

* ADR template variant `templates/adr.md` with a header row `Expires | YYYY-MM-DD`, `Service | <name>` and `Proposition | Prop. B.n`; ADR filename `ADR-nnnn-exception-<service>-<prop>.md`.
* Exception register: a table in `adr/README.md` generated by CI from every ADR whose header has an `Expires` row and status `Accepted`.
* Scheduled workflow `exception-expiry` (weekly): opens a GitHub issue assigned to the principal engineer team 30 days before each expiry, and marks the ADR `Status | Expired` on the day after.
* Conformance manifest schema: status value `exception ADR-nnnn` must reference an ADR that is `Accepted` and unexpired; the central index ([Prop. X.3](03-conformance-manifest.md)) re-validates nightly.

## Conformance

CI `adr-lint` requires the expiry row and 12-month bound on any exception ADR; the conformance index flags every manifest that references an expired or non-existent ADR.

## Scholium

Twelve months is long enough to schedule real work and short enough that the reason is still remembered at review. Whether renewal is limited is an open question.
