# Prop. IV.2 - Identifiers are ULID strings

| | |
|---|---|
| **Level** | MUST |
| **Status** | Accepted |
| **Since** | 2026-09-20 |
| **Owner** | Principal engineers |

## Statement

Every identifier ([Def. I.18](../../01-foundations/definitions.md#Def.%20I.18%20-%20Identifier)) exposed in a contract MUST conform to [`identifier.json`](../schemas/shared/v1/identifier.json): a 26-character ULID in Crockford base32, upper case, serialised as a JSON string. Identifiers MUST be generated by the system of record ([Prop. VII.9](../../07-data-ownership/propositions/09-ulids-from-system-of-record.md)) at creation time. Consumers MUST treat them as opaque: no parsing, no ordering assumptions beyond those the producer declares, no derivation of the creation time.

## Given

[Def. I.18](../../01-foundations/definitions.md#Def.%20I.18%20-%20Identifier), [Post. I.5](../../01-foundations/postulates.md#Post.%20I.5%20-%20Independent%20Evolution), [Post. II.5](../../02-api-guidelines/postulates.md#Post.%20II.5%20-%20Consumers%20We%20Do%20Not%20Deploy), [CN 3](../../01-foundations/common-notions.md#CN%203%20-%20Explicit%20Is%20Greater%20Than%20Implicit), [CN 5](../../01-foundations/common-notions.md#CN%205%20-%20One%20Concept%2C%20One%20Shape), [Prop. II.5](../../02-api-guidelines/propositions/05-cursor-pagination.md), [Prop. II.11](../../02-api-guidelines/propositions/11-json-conventions.md).

## Demonstration

One identifier shape across every contract is [CN 5](../../01-foundations/common-notions.md#CN%205%20-%20One%20Concept%2C%20One%20Shape). Among the candidates, integers leak count and ordering and overflow JavaScript's safe integer range ([Post. II.5](../../02-api-guidelines/postulates.md#Post.%20II.5%20-%20Consumers%20We%20Do%20Not%20Deploy)); UUID v4 is unordered, which makes it a poor clustering key and a poor keyset-pagination tie-breaker ([Prop. II.5](../../02-api-guidelines/propositions/05-cursor-pagination.md)); ULID is unique, URL-safe, fixed-width, string-typed ([Prop. II.11](../../02-api-guidelines/propositions/11-json-conventions.md)) and lexicographically ordered by creation time, which gives a total order when combined with any sort key. The ordering is a producer-side property; by [CN 3](../../01-foundations/common-notions.md#CN%203%20-%20Explicit%20Is%20Greater%20Than%20Implicit) a consumer may rely on it only where the contract says so, hence "opaque". ∎ Q.E.D.

## Corollaries

* **Cor. IV.2.1** - Database primary keys MAY be stored as 16-byte binary or as `uniqueidentifier`/`uuid` (a ULID is bit-compatible with a UUID); the contract still shows the 26-character string.
* **Cor. IV.2.2** - Externally assigned identifiers (a partner's order number, a VAT number) are *not* identifiers in this sense; they are string fields with their own schema and are never used as the resource id.

## Construction

.NET: `Ulid` from `Company.Contracts.Shared` (wrapping the `Ulid` NuGet package) with a `JsonConverter`, an EF Core value converter to `Guid`, and `Ulid.NewUlid()` using a monotonic generator per process. TypeScript: `type Identifier = string & { readonly __brand: "Identifier" }` plus a `isIdentifier()` guard.

## Conformance

Spectral `id-fields-are-shared-ref` (any property named `id` or `*Id` is a `$ref` to `identifier.json`). Catalogue CI validates the pattern.
